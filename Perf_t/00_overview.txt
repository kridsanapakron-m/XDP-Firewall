1. เครื่องและ IP
------------------------------------------------------------------------
ทุกเครื่อง: Ubuntu Server, CPU 8 core, NIC 1G, switch 1G เส้นเดียวต่อเครื่อง (eno1)

            A  client              B  LB (XDP native)       C  server
          192.168.100.10        192.168.100.20          192.168.100.30
                                VIP 192.168.100.100     backend 3 ตัวใน netns + cgroup

    backend    192.168.201.2 / 202.2 / 203.2  (netns server_1..3 บน C ต่อด้วย veth)
    ขาไป    A ──► B (ห่อ IPIP, src .20, DF) ──► C (xdp_lb_deencap ถอด) ──► backend
    ขากลับ  backend (src = VIP) ──► C ──► A  ไม่ผ่าน B (DSR)   nft/ipt: C ส่งขากลับผ่าน B
    core / คิว / IRQ
      A  pktgen thread t ใช้ tx queue t; wrk2 4 thread (ยิงตรง 3 ชุด: ชุดละ 2)
         route ไป VIP และ 192.168.200.0/22 ล็อก MTU 1480; ssh ไป B/C ใช้ connection ค้าง (ControlMaster)
      B  NIC 4 คิว, IRQ ของคิว q อยู่ core q (0-3), RSS udp4/tcp4 = sdfn (IP + port)
         xdp_lb_awfd core 4, irqbalance หยุด, governor performance
      C  NIC e1000e (บนเมนบอร์ด) มีคิวรับคิวเดียว ไม่มี RSS: IRQ เดียวอยู่ CPU 0, agent core 4, backend i อยู่ core 4+i (5 6 7) ตัวละ 1 core
         (CPUQuota 100% = 1 core เต็ม), nginx 1 worker + iperf -s ใน scope เดียวกัน

2. เป้าหมายรายข้อ
------------------------------------------------------------------------
  0    วัด C0 = throughput รวมเมื่อยิงตรง backend 3 ตัวพร้อมกันแบบ sat ต่อ scenario และ workload
  1.1  เทียบ CPU ของ B ต่อ packet ที่ส่งต่อสำเร็จ และ pps สูงสุดที่ loss_lb ≤ 0.1% ที่ pps/ขนาดเดียวกัน
  1.2  เทียบ CPU ของ B ต่อ request ของ HTTP 1 KB ที่ load เท่ากัน (keep-alive / close) และตัวที่ตันก่อน backend
  1.3  เทียบ CPU ของ B ต่อ Gbit/s ของ TCP stream ยาว
  1.4  วัด p50/p99 ที่เพิ่มขึ้นเมื่อผ่าน LB เทียบกับยิงตรง ที่ rate ต่ำคงที่
  2    วัดเวลาที่ใช้เลือก rule ต่อ packet (ns) เมื่อจำนวน VIP เพิ่ม ด้วย flow ใหม่ (ทุก packet ต้องหา rule)
  3    แยกต้นทุนต่อ packet ของแต่ละขั้นของ xdp_lb, ต้นทุนและการส่งถึงของ fragment handling
  4    เทียบ latency, error, balance ของ LB และอัลกอริทึมตัวแทนของแต่ละ LB ที่ load เท่ากันเป็น % ของ C0
       เมื่อ backend เป็นตัวจำกัด (ไม่ใช่สาย 1G)  backend เท่ากัน (4.1) / ไม่เท่ากัน (4.2 4.3 4.5) / เปลี่ยนกลางรอบ (4.4)  เทียบกับ baseline ไม่ผ่าน LB (4.0)

3. ขอบเขตระบบ
------------------------------------------------------------------------
  ข้างใน    B: xdp_lb (prog + maps), xdp_lb_awfd, ตัวเปรียบเทียบ ipvs nft ipt nginx haproxy
            C: xdp_lb_deencap และ xdp_lb_agent
  ข้างนอก   client A และเครื่องมือยิง, switch, nginx/iperf ใน backend, stack ของ C (ถือว่าคงที่)
  จุดอ้างอิงที่ไม่มี LB: ข้อ 0, 1.4 (direct), 3.0

4. service และ outcome
------------------------------------------------------------------------
  service: รับ packet/connection ของ VIP ส่งไป backend ที่ถูก และคง flow ไว้กับ backend เดิม
  correct      ส่งถึงและคง flow       sent_pps lb_cores ns_per_fwd_pkt cpu_us_per_req p50/p99/p99.9 balance Ω
  incorrect    flow ย้าย/fragment แยก  frag_miss frag_delivery_pct conn_new_ratio (ผิดเกณฑ์) icmp_ratio
  unavailable  drop/timeout/เต็ม       loss_lb loss_e2e error_rate c_rx_drops frag_store_failed

5. metric (report.py ใช้นิยามเดียวกัน)  HB = มากดี  LB = น้อยดี  NB = ใกล้ค่าที่คาดดี
------------------------------------------------------------------------
  sent_pps        packet/datagram ที่ A ยิงได้จริง ÷ เวลายิง (pktgen รวม "Npps" ทุก thread)   pps   NB ≥95%
  lb_cores        core ที่ B ใช้ (mpstat เฉลี่ยรายวินาทีช่วงยิง: 100 − %idle − %iowait)       core  LB
                  − core เฉลี่ยของรอบ idle ของข้อและ mode เดียวกัน
  lb_usr lb_sys   lb_cores แยกชนิด: %usr+%nice, %sys, %irq+%soft (หัก idle แต่ละชนิด)          core  LB
  lb_soft         xdp ipvs nft ipt อยู่ใน soft เกือบทั้งหมด  nginx haproxy มี usr+sys ด้วย
  ns_per_fwd_pkt  lb_cores × เวลายิงจริง (ns) ÷ packet ที่ส่งต่อ                             ns    LB
                  ส่งต่อ = xdp_redirect ของ xdp_lb_ctl stats (xdp) หรือ tx_packets ของ NIC (mode อื่น)
  ns_per_rx_pkt   เหมือนข้างบนแต่หารด้วย packet ที่ B รับ (ข้อ 3.4)                         ns    LB
  xdp_ns          run_time_ns ÷ run_cnt ของ prog (bpf_stats ข้อ 2 และ 3)                   ns    LB
  lookup_ns       ข้อ 2: เวลาเฉลี่ยต่อครั้งของฟังก์ชันประเมิน rule (bpftrace fentry/fexit)    ns    LB
                  nft = nft_do_chain ของ table perf_lb, ipt = ipt_do_table ของ nat PREROUTING
                  xdp = xdp_ns (ทั้งโปรแกรม)  d_lookup_ns = ต่างจาก VIP 1 ของ mode และ pattern เดียวกัน
                  lookup_calls_per_pkt = ครั้ง ÷ packet ที่ B รับ (ควร ≈ 1)
  cpu_us_per_req  lb_cores × เวลายิงจริง (µs) ÷ request ที่สำเร็จ                          µs    LB
  cores_per_gbit  lb_cores ÷ (Mbit/s ÷ 1000)                                               core  LB
  loss_lb         (rx + rx_missed − ส่งต่อ) ÷ (rx + rx_missed) ที่ NIC ของ B                %     LB
  loss_e2e        (sent − datagram ที่ backend นับใน udp_in) ÷ sent                        %     LB
  conn_new_ratio  conn_new ÷ (conn_hit + conn_new)   เกณฑ์ EST ≤ 0.01, NEW ≥ 0.95           -     NB
  q_share         rx ต่อคิวของ B ÷ rx รวม (q_max_share = คิวที่มากสุด)                    %     NB 100/คิว
  avg_pkt_bytes   rx_bytes ÷ rx_packets ที่ NIC ของ B (ไม่รวม FCS)                          B     NB
  a_cores c_cores core ที่ A / C ใช้ทั้งเครื่อง (mpstat แบบเดียวกับ B ไม่หัก idle)            core  NB
  cpu_window      mpstat ของ A B C ต้องเก็บได้ ≥ เวลายิง − 1 วินาที ไม่งั้นตัดรอบนั้น          -     -
  c_rx_drops      rx_dropped + rx_missed_errors ของ NIC ของ C                              pkt   LB
  req_s mbps      Requests/sec, Transfer/sec ของ wrk2/h2load และ [SUM] ของ iperf (goodput)  -     HB
  p50 p99 p99.9   percentile ของ latency จาก histogram ของทุกชุดรวมกัน (ไม่แสดงในแถว sat)   ms    LB
  error_rate      (socket error + non-2xx) ÷ (request + error)                              %     LB
  frag_delivery   datagram ที่ backend ประกอบได้ (udp_frag_in) ÷ datagram ที่ส่ง           %     HB
  cpu0_pct        % เวลาทำงานของ core 0 ของ B = ref-cycles ÷ (วินาที × TSC) เฉลี่ยรายวินาที  %     LB
                  (perf stat ข้อ 1.6 3.2 3.3 ที่ B ใช้ core 0 core เดียว ไม่ขึ้นกับ turbo)
  cpu_cores       core ของ B ที่ใช้รวมทุก CPU (perf stat ข้อ 3.5 และชุด 3.2/3.3-allcore)        core  LB
                   cpu_hot_pct = % ของ CPU ที่ทำงานมากสุด
  cpu_ns_per_pkt  เวลาทำงานของ CPU รวม ÷ packet ที่มาถึง B   cpu_ns_per_datagram ÷ datagram   ns    LB
  icmp_ratio      icmp_sent ÷ packet ที่ส่ง  (1490 B ≈ 1, 1470 B = 0)                      -     NB
  b<i>_util       CPU ของ backend i ÷ quota                                               -     NB
  b<i>_req_pct    request ที่ backend i ตอบ ÷ รวม (nginx stub_status)                     %     NB ∝ quota
  b<i>_conn_pct   connection ที่ backend i รับ (accepts) ÷ รวม = การตัดสินใจของ LB ตอนเปิด connection  %  NB ∝ quota
                  (stub_status เดียวกัน  เริ่มเก็บ 2026-11-02 ชุดก่อนหน้าไม่มี)
  b<i>_throttled_pct  เวลาที่ backend i ถูกหยุดเพราะใช้ CPU เกิน quota ÷ เวลา (cgroup cpu.stat) %  LB
  balance         util สูงสุด ÷ util เฉลี่ย (1 = แบ่งตาม capacity พอดี)                    -     LB
  C0              ผลรวม throughput ของ 3 backend ที่ยิงตรงพร้อมกันแบบ sat (เก็บใน c0.tsv)    req/s HB
                  link-bound = goodput ของ C0 ≥ 90% ของ 940 Mbit/s: แยกอัลกอริทึมไม่ได้
  Ω               throughput ÷ C0 (sat เท่านั้น  4.4 ถ่วง C0 ตามเวลาก่อน/หลังเปลี่ยน quota)  -     HB
  convergence_s   เวลาจากเปลี่ยน quota จนถึงต้นช่วงที่ balance ≤ 1.1 ติดกัน 3 วินาที (.ts)    s     LB
  usable capacity pps สูงสุดใน PPS_LADDER (64 B) ที่ loss_lb เฉลี่ย ≤ 0.1%                    pps   HB
  gap_ms          เวลาเสียระหว่างรอบ: t_end ของรอบก่อน ถึง t_start ของรอบนี้                 ms    LB
  sat = closed-loop ยิงเร็วสุดเท่าที่ระบบตอบทัน (wrk2 -R สูงเกินจริง / h2load ไม่ใส่ --rps / iperf)
        อ่านได้เฉพาะ throughput และ CPU: latency ≈ connection ÷ throughput (Little's law) จึงไม่แสดง

13. สมมติฐานและข้อจำกัด
------------------------------------------------------------------------
  - link 1G เส้นเดียว: B รับและส่งทาง eno1 เดียว ขาออกหลังห่อ IPIP (~1.20 Mpps ที่ 64 B) คือเพดาน
  - xdp/ipvs เป็น DSR (B เห็นแค่ขาไป) ส่วน nft/ipt/nginx/haproxy ขากลับผ่าน B ด้วย
    CPU ต่อ request จึงเป็นต้นทุนรวมของแต่ละแบบ ไม่ใช่ต้นทุนต่อ packet ที่เทียบกันตรง ๆ
  - NIC ของ C เป็น e1000e คิวเดียว (ethtool -l ไม่รองรับ, IRQ เดียวบน CPU 0): การรับ, XDP ถอด IPIP (generic)
    และการประกอบ fragment ของ C ทำบน core เดียว  เกิน ~500k packet/s (64-90 B) NIC ของ C ทิ้ง (rx_missed_errors)
    ตัวเลขฝั่ง backend (loss_e2e, frag_delivery_pct) ที่อัตราสูงจึงเป็นเพดานของ C ไม่ใช่ของ LB  เช่น 1.1 ที่ 1M
    loss_e2e ~49% ขณะที่ loss_lb ≈ 0  ข้อ 3.3 3.5 จึงยิงไม่เกิน 400k packet/s  (ตรวจ 2026-10-29)
  - tcpreplay บน A ยิง frame 90 B ได้ ~700k packet/s (ตรวจ 2026-10-29)
  - backend 3 ตัวอยู่บน C เครื่องเดียว ใช้ NIC/IRQ ร่วมกัน  traffic เป็นแบบสังเคราะห์ (ไฟล์คงที่, flow ไล่ลำดับ)
  - deencap บน veth เป็น generic XDP; bpf_stats เพิ่ม overhead ต่อ packet ตัวเลขข้อ 2, 3 เทียบตรงกับข้อ 1 ไม่ได้
  - ผลใช้ได้กับ 1G / 8 core / ค่าในหัวข้อ 6 เท่านั้น
  - ชุดใหม่: xdp (ช่วง A) กับตัวเปรียบเทียบ (ช่วง B) วัดคนละช่วงเวลาเพื่อลด reset การ์ด  drift ตามเวลาจึงปนกับ mode ได้
    บันทึก env-a/b/c.txt ทุกข้อไว้เทียบ  B ของชุดใหม่ใช้ kernel 6.8.0-147 (ผลชุดเก่าใช้ 6.8.0-139)
  - TCP ไป VIP ล็อก MTU 1480 บน A ทุก mode: IPVS tunnel ส่ง ICMP frag-needed เอง แต่ xdp (pmtu ปิด) ไม่ส่ง
    ถ้าไม่ล็อก ขนาด packet ของสอง mode จะต่างกัน (ดู avg_pkt_bytes ของ 1.3)  ข้อ 3.4 ปลดล็อกชั่วคราว
  - wrk2 ใช้ ~10 s แรกปรับเทียบ (latency นับ ~30 s ของรอบ 40 s) ส่วน req/s และ CPU นับทั้งรอบ  pilot เทียบ 40/60 s
    h2load (ถ้าไม่มี wrk2) วัด latency จากตอนส่ง request จึงไม่แก้ coordinated omission
  - ข้อ 2 ขอบเขตที่จับเวลาไม่เท่ากัน: xdp = ทั้งโปรแกรม (parse, หา VIP, conn_map, ห่อ IPIP, redirect)
    nft/ipt = ฟังก์ชันประเมิน rule อย่างเดียว (ไม่รวม conntrack, NAT, routing)  ผลหลักคือ d_lookup_ns ใน mode เดียวกัน
    fentry/fexit เพิ่มเวลาราวสิบ ns ต่อครั้งเท่ากันทุกจำนวน VIP  ipt ใช้ iptables-legacy (ipt_do_table ไล่ rule ทีละข้อ)

  - ข้อ 4 เทียบทั้งระบบ: ผลปนระหว่างอัลกอริทึมกับสถาปัตยกรรม (xdp/ipvs DSR, nft/ipt ขากลับผ่าน B, nginx/haproxy proxy ที่รู้
